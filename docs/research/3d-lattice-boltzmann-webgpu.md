# Sixteen-bit storage puts a live 3D tunnel on an M5

A base M5 laptop can run an interactive D3Q19 wind tunnel of about 2 million cells at 60 fps if the populations are stored in 16 bits. That grid (192×96×96) gets about 10 time steps per frame and a flow-through time of about 3 seconds. The M5's GPU has **153 GB/s** of memory bandwidth ([Apple](https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/)). FluidX3D measures **800 D3Q19 MLUPS in FP32 and 1,596 with FP16 storage** on it ([FluidX3D README](https://raw.githubusercontent.com/ProjectPhysX/FluidX3D/master/README.md)), and this repo's D2Q9 benchmark shows that WebGPU in Chrome reaches the same fraction of peak bandwidth as native code ([slowernet/cells PR #1](https://github.com/slowernet/cells/pull/1)). The existing solver design carries over almost unchanged: the `f_i − w_i` shift that makes 16-bit storage accurate is already in place ([Lehmann et al., arXiv:2112.08926](https://arxiv.org/pdf/2112.08926)), A/B pull streaming stays, TRT with Λ = 3/16 needs no retuning, and Bouzidi links and momentum exchange work per link in any dimension. The changes that matter are FP16S storage through WGSL `f16`, a new flag layout (the 2D bit budget leaves only 10 bits for force slots once D3Q19 needs 19 direction bits), raised buffer limits, and a visualization layer built from slices, tracers and an occasional Q-criterion isosurface. Two choices carry real risk. Esoteric Pull in-place streaming conflicts with the fused Bouzidi kernel and buys memory the demo does not need. D3Q19 loses rotational invariance above Re ≈ 250 around round bodies, so the demo's high-Re runs will be qualitative unless it pays about 1.4× for D3Q27. No browser 3D LBM project has published a measured throughput, so a 3D benchmark would again be a first.

## A base M5 sustains about 1,600 D3Q19 MLUPS

LBM is bandwidth bound, and the arithmetic is simple. FluidX3D's D3Q19 kernel moves **153 bytes per cell per step in FP32 and 77 bytes with 16-bit storage**, and runs at 2.4 to 16.6 FLOPs per byte, so "performance is only limited by memory bandwidth" ([FluidX3D README](https://github.com/ProjectPhysX/FluidX3D)). This solver's A/B layout with a 4-byte flag word moves 19 × 8 + 4 = 156 bytes in FP32 and 80 bytes in FP16. On Apple GPUs, FluidX3D's native OpenCL kernel reaches 76 to 92% of data-sheet bandwidth:

The M5 Pro and Max rows scale the base M5's 80% efficiency by Apple's bandwidth figures; nobody has measured them. FluidX3D has no M3 or M4 rows. For those chips only search snippets give bandwidth: M3 Pro at 150 GB/s ([MacRumors](https://www.macrumors.com/2023/10/31/apple-m3-pro-less-memory-bandwidth/), search snippet only), M3 Max at 300 or 400 GB/s ([Apple](https://support.apple.com/en-us/117737), search snippet only), and M4 Pro and Max at 273 and 546 GB/s ([Apple](https://www.apple.com/newsroom/2024/10/apple-introduces-m4-pro-and-m4-max/), search snippet only). The M5 base chip is the one to size for, because "M5 laptop" spans a 4× bandwidth range from the base chip to the 40-core Max.

WebGPU does not appear to cost bandwidth. This repo's D2Q9 kernel runs at 97 to 100% of a copy-only kernel that moves the same 76 bytes per cell, **about 1,700 MLUPS on grids larger than cache** ([slowernet/cells PR #1](https://github.com/slowernet/cells/pull/1)). That is about 129 GB/s, or 84% of the M5's peak, slightly above FluidX3D's native 80%. Two cautions come from the same measurement. The 3,400 MLUPS that a cache-resident 512×256 grid reached will not recur in 3D, because every useful 3D grid is hundreds of megabytes. And when the step budget left the GPU partly idle, the M5 down-clocked and throughput fell from 1,311 to 674 MLUPS ([slowernet/cells PR #1](https://github.com/slowernet/cells/pull/1)), so the 3D mode needs the same auto step control that fills 85% of the frame. Per-dispatch overhead on Metal is **32 to 71 µs** ([Maczan, arXiv:2604.02344](https://arxiv.org/abs/2604.02344)), which stays small at 10 dispatches per frame in one compute pass. 3D stencils touch neighbors in three planes, so the D2Q9 efficiency may not carry over exactly; only a WebGPU D3Q19 benchmark will settle it.

The browser record contains design targets and no measurements. windtunnel_vis runs D3Q19 in WebGPU on a default 256×128×128 grid with a "45 fps target" for "laptop GPUs of the RTX 3070 Ti class", and drops to 144×64×72 or 96×48×48 below about 12 fps, but reports no achieved fps, steps per second or MLUPS ([windtunnel_vis](https://github.com/Om-anand-0/windtunnel_vis)). urban-wind-lab solves D3Q19 in a Web Worker with WebGL2 and calls its results "unvalidated" and "qualitative" ([urban-wind-lab](https://github.com/arch85-km/urban-wind-lab)). AquaEmbodied-WebGPU runs FP32 D3Q19 with a free surface and Smagorinsky LES, again without throughput figures ([AquaEmbodied-WebGPU](https://github.com/dongwang22/AquaEmbodied-WebGPU)).

192×96×96 is the size that feels live. At 256×128×128, the windtunnel_vis default, a gust takes ten seconds to cross the tunnel, which reads as sluggish in a demo where users switch presets. In FP32 the same grids run at half these step rates.

## FP16S storage doubles speed; in-place streaming mainly saves memory

Lehmann et al. stored D3Q19 populations in 16 bits while keeping all arithmetic in FP32. On "the vast majority of hardware", they reached the theoretical 80% speedup, and 16-bit results matched FP32 in most of six test cases, including a 128³ lid-driven cavity at Re 1000, where deviations appeared in the fourth digit ([Lehmann et al., arXiv:2112.08926](https://arxiv.org/pdf/2112.08926)). The precondition is the population shift that this solver already uses. The paper calls storing `f_i − w_i` "absolutely crucial for the 16-bit compression" and says the equilibrium must follow its eq. 3 "exactly as presented without changing the order of operations … otherwise the accuracy may not be enhanced at all" ([arXiv:2112.08926](https://arxiv.org/pdf/2112.08926)). Without the shift, a microcapsule case failed outright. The 16-bit formats did degrade in three places: centre-line error in large-radius Poiseuille flow, the energy floor of a decaying Taylor-Green vortex, and low-level vorticity noise in a Kármán street ([arXiv:2112.08926](https://arxiv.org/pdf/2112.08926)). The paper used SRT, mid-grid bounce-back and equilibrium boundaries. It did not test TRT, Bouzidi walls, Zou-He boundaries or force coefficients, so the effect on C_D and C_L has to be measured here.

FP16S is the right format. It is IEEE half precision scaled by 2^15, so shifted populations, which obey |f − w| ≲ 0.34ρ, fill the range ±2 and stay clear of subnormals. It "comes at no additional computational cost" ([arXiv:2112.08926](https://arxiv.org/pdf/2112.08926)). FluidX3D's store and load are a multiply by 32768 and 1/32768 around the hardware conversion ([FluidX3D lbm.cpp](https://github.com/ProjectPhysX/FluidX3D/blob/master/src/lbm.cpp)). The custom FP16C format halves truncation error but needs software encoding, and on the M1 Max and M2 Max it fell to near-FP32 speed ([FluidX3D README](https://github.com/ProjectPhysX/FluidX3D/blob/master/README.md)).

WGSL offers two routes. With the `shader-f16` device feature and `enable f16;`, `array<f16>` is legal in storage buffers, with 2-byte alignment ([WGSL §14.4.1](https://gpuweb.github.io/gpuweb/wgsl/#alignment-and-size)), so the SoA layout `f[i * N + cell]` survives unchanged. Neighbouring threads that write the two halves of one 32-bit word touch different memory locations, so WGSL does not treat those writes as a data race. The feature shipped in Chrome 120 ([Chrome](https://developer.chrome.com/blog/new-in-webgpu-120)). Web3D Survey reports it in 99.98% of Safari sessions and 99.85% on macOS, against 70.5% on Linux and 86.6% on Android ([Web3D Survey](https://web3dsurvey.com/webgpu/features/shader-f16)). Apple says it is "supported on all Apple devices" ([WWDC25](https://developer.apple.com/videos/play/wwdc2025/236/), search summary only). The core-language fallback, `pack2x16float`, needs no feature. windtunnel_vis uses it to pack two x-adjacent cells per `u32`, with each thread updating a cell pair so that every store writes a full word ([windtunnel_vis wgslLbm.ts](https://github.com/Om-anand-0/windtunnel_vis/blob/HEAD/src/solver/wgslLbm.ts)). Pairing cells doubles register pressure, and x-shifted pulls fetch whole words and discard half, so it is the slower route for a Mac-first demo.

WGSL gives weaker numeric guarantees than OpenCL, and three of its rules shape the kernel. First, f32 to f16 conversion has no specified rounding mode, and extra significand bits "may be discarded" ([WGSL §15.7](https://gpuweb.github.io/gpuweb/wgsl/#floating-point-conversion)). Lehmann's accuracy figures assume OpenCL's round-to-nearest-even, so a truncating backend adds a one-sided bias of up to one ulp per store. No per-backend table of rounding behaviour exists. Second, packing, unpacking and conversions may flush subnormals to zero ([WGSL §15.7.2](https://gpuweb.github.io/gpuweb/wgsl/#differences-from-ieee754)), which makes the 2^15 scaling more important in WGSL than in OpenCL. windtunnel_vis stores unscaled FP16 and could lose small `f − w` values on a flushing backend. Third, `pack2x16float` returns an indeterminate value for out-of-range input ([WGSL §17.9.9](https://gpuweb.github.io/gpuweb/wgsl/#pack2x16float-builtin)), and the finite-math assumption makes an overflowed `f16` indeterminate too. A diverging run can therefore write garbage without a clean NaN. A `clamp` before each store costs one ALU operation and no load, which fits the hot-path rules. Force reductions are unaffected: WGSL atomics are `u32` and `i32` only ([WGSL §6.2.8](https://gpuweb.github.io/gpuweb/wgsl/#atomic-types)), and the current reduction writes per-slot values without float atomics.

Esoteric Pull is the in-place streaming scheme to know about, and the demo should not adopt it yet. It keeps one population buffer and one fused kernel: each cell loads its positive directions locally and pulls its negative ones from neighbours, collides, then stores in the opposite pattern, with the orientation flipped by time-step parity ([Lehmann 2022, Computation 10, 92](https://doi.org/10.3390/computation10060092)). On an A100 it ran at 97% of one-step pull ([Lehmann 2022](https://doi.org/10.3390/computation10060092)). Its wins are memory, from 169 to 55 bytes per D3Q19 node when combined with FP16, and cache gains on integrated GPUs and CPUs. The paper tested no Apple GPU, and its per-device iGPU gains could not be read from the text. Traffic per step barely changes: FP16 halves it whether streaming is A/B or in place. The costs fall on exactly the features this tunnel has. The Bouzidi branch for q < 0.5 reads the post-collision `f_opp` at the next fluid node x + c_i (`src[j * N + n]` in `src/shaders/step.ts`). Under Esoteric Pull that value sits in a parity-dependent slot that a concurrent thread may overwrite in the same step. FluidX3D hit the same race in its free-surface code and fixed it with an extra kernel that cost about 20% ([Lehmann 2022](https://doi.org/10.3390/computation10060092)). Init, refill, readbacks and render kernels would all need parity-aware loads and stores, and ρ and u can no longer be summed from local slots ([FluidX3D kernel.cpp](https://github.com/ProjectPhysX/FluidX3D/blob/master/src/kernel.cpp)). Nobody has published Bouzidi or Zou-He combined with Esoteric Pull, or a WGSL implementation of it. At 192×96×96, FP16 A/B needs 134 MB of populations, so memory does not justify that work.

Buffer limits do require attention. WebGPU's default `maxStorageBufferBindingSize` is **128 MiB** ([W3C WebGPU](https://www.w3.org/TR/webgpu/)). One FP32 D3Q19 population copy at 192×96×96 is 134,479,872 bytes, just over that limit; the FP16 copy is half that and fits. Anything larger, or FP32 at this size, must request the adapter's higher limits at `requestDevice`. What Chrome and Safari expose on an M5 was not found and should be logged at startup.

## What the port changes in this solver

Most of the solver generalizes by regenerating the unrolled kernel from D3Q19 tables. The collision is unchanged: FluidX3D's 3D TRT kernel hard-codes Λ = 0.1875 for every velocity set ([FluidX3D kernel.cpp](https://raw.githubusercontent.com/ProjectPhysX/FluidX3D/master/src/kernel.cpp)), and the new weights (1/3, 1/18, 1/36) go into the `f_i − w_i` shift. Bouzidi reuses the SDF-derived fraction q per link; only the diagonal links are new. Momentum exchange gains a z component. For a stationary body, Wen's Galilean-invariant form reduces to the standard one, "only uses local data and is independent of boundary geometries", and was validated in 3D ([Wen et al., arXiv:1303.0625](https://arxiv.org/pdf/1303.0625)). With shifted storage, each link adds a 2w_i c_i term that cancels only over a closed surface, so whole-body sums are safe and partial-surface sums (per-panel forces) need it added back. That last point comes from algebra on Wen's formula; no source states it.

Three items need new design, each an inference from the current code. The flag word runs out of room. In 2D, bits 0 to 8 mark directions, bits 9 to 11 mark SOLID, INLET and OUTLET, and the force-slot index starts at bit 12 (`src/lattice.ts`). D3Q19 needs 19 direction bits, which leaves 10 bits, or 1,023 force slots. A sphere 24 cells across has roughly π·24² ≈ 1,800 boundary cells, so the slot index must move to its own `u32` buffer. The kernel reads that buffer only on the slow path, which keeps the fast path at one flag load. `cellForce` becomes a `vec3f` array with a 16-byte stride. Macro fields for rendering should be written by the last step of each frame, in a pipeline variant selected by an override constant, the way FluidX3D's `UPDATE_FIELDS` computes ρ and u inside `stream_collide` ([FluidX3D kernel.cpp](https://github.com/ProjectPhysX/FluidX3D/blob/master/src/kernel.cpp)). A separate macro pass would re-read every population once per frame. Finally, the Reynolds range shrinks. With u = 0.1 and the τ ≥ 0.51 clamp, Re_max = 3uD/(τ − ½) = 30D, so a 16-cell sphere tops out near Re 480 and a 24-cell one near 720. Reaching 10^4 needs Smagorinsky LES, and the UI should label those runs qualitative.

Domain proportions change too. The 2D validation found that a cylinder 8D from the inlet read St 3% high and C_D 5% high, and matched references at 16D in a 48D-wide domain (AGENTS.md). A 192×96×96 grid with a 16-cell sphere allows only about 4D upstream and 6D of width. A 3D body disturbs the flow less at a given distance than a 2D one, which should soften the confinement (an inference; nobody has measured it for this solver). The validation suite needs its own 3D ranges, fixed before the first run.

## Slices and tracers are nearly free; isosurfaces need budgeting

At 2 to 10 million cells, rendering competes with the solver for the same bandwidth, so the choice of views sets how many steps survive per frame. Axis-aligned slice planes of speed or vorticity read a few hundred thousand cells each. That costs almost nothing next to a step, and a slice gives the most readable quantitative view. Tracer particles are also cheap: 10^4 to 10^5 particles advected with RK2 and trilinear sampling read well under 1% of a step's bytes (estimate). Smoke released from a rake upstream of the body gives the most intuitive picture of shedding. Instantaneous streamlines of an unsteady wake can mislead, because they are not streaklines. windtunnel_vis combines heatmap slices, surface C_p, "approximately 100,000+ smoke tracer particles with trails", rake streamlines and Q isosurfaces ([windtunnel_vis](https://github.com/Om-anand-0/windtunnel_vis)), which confirms that the mix is feasible in a browser, though the project reports no per-view costs.

Isosurfaces show 3D vortex structure best, and the literature favours Q or λ2 over vorticity magnitude. Vorticity also lights up boundary layers and shear layers and hides vortex cores; early studies dropped it for "its poor ability to distinguish between vortex cores and shear motions" ([arXiv:1805.03984](https://arxiv.org/pdf/1805.03984), search snippet only). λ2 needs an eigenvalue solve per cell and is "the most restrictive" criterion ([Chakraborty et al., JFM 2005](https://www.oist.jp/sites/default/files/img/pages/units/fm/chakraborty-pinaki-pubs/vortex_identification_jfm05.pdf), search snippet only), and with consistent RMS-normalized thresholds the criteria become "equally efficacious" (same source, search snippet only). Q = ½(|Ω|² − |S|²) is cheaper and is what FluidX3D renders, coloured by velocity ([FluidX3D README](https://github.com/ProjectPhysX/FluidX3D)).

The cost of isosurfaces depends on the method. Will Usher's WebGPU marching cubes (mark, scan, compact, emit) takes **40.8 to 54.4 ms on an M2 Max** and 31 to 37.5 ms on an RTX 3080 for a 256³ volume, within a few milliseconds of native Vulkan ([Usher](https://www.willusher.io/graphics/2024/04/22/webgpu-marching-cubes/)). Scaled linearly to 2M cells, that is roughly 5 to 7 ms on an M2 Max (estimate), too much to spend every frame. FluidX3D skips compaction. Each cell runs marching cubes on its 2×2×2 Q stencil and rasterizes its 0 to 5 triangles straight into a software z-buffer. Computing Q naively loads 32 velocities per cell, and tiling them in local memory cut that to 2.6 loads and made the kernel up to 2× faster ([FluidX3D releases](https://github.com/ProjectPhysX/FluidX3D/releases)). The WebGPU equivalent is to compute Q into a scalar buffer once, emit triangles with `atomicAdd` into a preallocated vertex buffer, and let a one-thread pass write the count into `drawIndirect` arguments. The CPU never reads the count back, so the no-readback rule holds. Refreshing the surface every few frames, or at half resolution, keeps it inside the 3 ms render budget. Full volume ray marching at 1080p would take on the order of a billion trilinear fetches per frame (estimate), comparable to a whole step, and nobody has published a WebGPU cost for it on simulation grids.

The orbit view needs obstacles drawn with correct occlusion. Preset bodies have analytic SDFs, so a fullscreen fragment pass can sphere-trace them and write `@builtin(frag_depth)`, and tracers, slices and isosurface triangles then depth-test against the body in the same pass (inference; no WebGPU example was found). Read-write storage buffers are invisible to vertex shaders ([W3C WebGPU](https://www.w3.org/TR/webgpu/)), so geometry drawn from compute output needs read-only bindings, as the 2D line renderer already does. Hardware trilinear filtering of 32-bit float textures needs the optional `float32-filterable` feature ([webgpufundamentals](https://webgpufundamentals.org/webgpu/lessons/webgpu-limits-and-features.html), search snippet only), so velocity sampling should use `rgba16float` or manual interpolation from the macro buffer.

## D3Q19 suffices at Re 100; round bodies at higher Re want D3Q27

D3Q19 is the production default: FluidX3D ships it with SRT and offers D3Q27 and TRT as options ([FluidX3D README](https://github.com/ProjectPhysX/FluidX3D)). Its known defect is rotational invariance. White and Chong found that at Re ≥ 250, D3Q15 and D3Q19 gave different answers depending on flow alignment with the lattice planes, while D3Q27 did not, and none of the lattices diverged at Re 50 ([J. Comput. Phys. 2011](https://www.sciencedirect.com/science/article/abs/pii/S0021999111002798), search snippet only). Kang and Hassan found D3Q19 "produced unreasonable data" in turbulent pipe flow, where D3Q27 matched DNS ([J. Comput. Phys. 2013](https://sciencedirect.com/science/article/abs/pii/S0021999112003968), search snippet only). A 2026 review sums it up: "if the walls are misaligned or strong rotational features are present, D3Q27 is generally more suitable" ([Wind Energ. Sci. 2026](https://wes.copernicus.org/articles/11/983/2026/)). Bauer and Rüde derived a D3Q19 equilibrium from the continuous Maxwellian that is "more accurate than the widely used second order equilibrium, while having the same computation costs" ([arXiv:1803.04937](https://arxiv.org/abs/1803.04937)), and a follow-up attributes the square-duct artifacts to the form of the equilibrium, with the velocity set itself not at fault ([J. Comput. Phys. 2020](https://www.sciencedirect.com/science/article/abs/pii/S0021999119308162), search snippet only). The corrected equilibrium.s interaction with the `f − w` shift and Lehmann's operation order is untested.

For this demo the trade is concrete. Spheres, cylinders and cars are exactly the misaligned, rotational geometry where D3Q19 fails, but only above Re ≈ 250, and the grid caps Re near 500 to 700 without LES anyway. D3Q27 moves 27/19 ≈ 1.42× the bytes, so on an M5 with FP16 it drops to about 1,150 MLUPS and 192×96×96 falls to about 7 steps per frame (estimate). The kernel generator should take the velocity set as a parameter, with D3Q19 as the default and D3Q27 as a quality toggle. TRT carries over to both sets unchanged, since Λ acts on opposite-direction pairs.

At the open boundaries, the literature favours robustness over formal order. Hecht and Harting extended Zou-He to D3Q19 faces: local, second order, with "no artificial slip" ([arXiv:0811.4593](https://arxiv.org/abs/0811.4593)). Their abstract does not cover the 12 edges and 8 corners, where density is undetermined. Latt et al. compared five straight velocity boundaries and found that schemes replacing every population on the node are "much better" for stability at high Re ([Phys. Rev. E 77, 056703](https://link.aps.org/doi/10.1103/PhysRevE.77.056703), search snippet only). FluidX3D uses plain equilibrium cells for both inflow and outflow, and describes them as absorbing "any incoming shockwaves" ([FluidX3D DOCUMENTATION.md](https://raw.githubusercontent.com/ProjectPhysX/FluidX3D/master/DOCUMENTATION.md)). That claim has no published reflection coefficient, and a cell pinned to ρ = 1 should reflect pressure waves in theory. Equilibrium stresses are zero, which "creates an inconsistency if the inflow is not uniform" ([WES 2026](https://wes.copernicus.org/articles/11/983/2026/)); a uniform ramped inflow avoids that. For the outlet, a sponge "helps to avoid non-physical reflections" ([WES 2026](https://wes.copernicus.org/articles/11/983/2026/)), and regularized characteristic conditions were the only variant tested that handled Re 10^5 ([Wissocq et al., arXiv:1701.07734](https://arxiv.org/abs/1701.07734)). The 2D finding that cylinder lift grows without bound unless weak absorbing layers are present should hold in 3D, since a box adds transverse resonant modes.

Side walls in a free-flight tunnel can be slip, periodic or equilibrium far-field. Slip walls bounce populations "forward" instead of back ([WES 2026](https://wes.copernicus.org/articles/11/983/2026/)), which the current `MIRROR_Y` code already does for one axis. Where two slip walls meet, a diagonal link reflects in both normal components, which equals bounce-back for that link; the per-direction flag bits can encode this. Periodic sides place image bodies at one tunnel width, which at 6D is close. Equilibrium side cells at u = U∞ behave closest to free flight and have the simplest edge and corner logic. No source compares these for 3D external aerodynamics.

## Recommendations for the 3D mode, in priority order

| Priority | Decision | Recommendation |
|---|---|---|
| 1 | Benchmark first | Port the MLUPS sweep to D3Q19 FP32 and FP16 before building the UI; target about 800 and 1,600 MLUPS on a base M5 |
| 2 | Storage | FP16S (`array<f16>`, ×2^15 on store, clamp before store) with A/B pull streaming; FP32 stays the validated reference; `pack2x16float` pairing only if non-Apple support matters |
| 3 | Grid | 192×96×96 default (about 10 steps per frame on a base M5), 128×64×64 fallback, larger grids scaled to measured bandwidth; request raised buffer limits |
| 4 | Lattice and collision | D3Q19 + TRT (Λ = 3/16) by default, D3Q27 as a generator switch; Smagorinsky above Re ≈ 30D; label high-Re runs qualitative |
| 5 | Solver data | Move force-slot indices to their own buffer (read on the slow path only); `vec3f` forces; macro fields written on the last step of each frame |
| 6 | Boundaries | Ramped equilibrium inlet (Hecht-Harting Zou-He face for validation runs), Zou-He or equilibrium outlet at ρ = 1 with a weak absorbing layer, slip or equilibrium side walls |
| 7 | Visualization | Orbit camera; sphere-traced analytic obstacles writing depth; speed and vorticity slices; rake-seeded tracers; Q isosurface refreshed every few frames via `atomicAdd` and `drawIndirect` |
| 8 | Validation | Square-duct Poiseuille, 3D Taylor-Green, 128³ cavity at Re 1000, sphere drag; ranges fixed before runs, and FP16 C_D compared against FP32 |
| 9 | Defer | Esoteric Pull, D3Q19 Bauer-Rüde equilibrium, volume ray marching, cumulant collision |

**Throughput and sizing.** Size for the base M5 and scale up with measured throughput, because the same "M5 laptop" label spans 153 to 614 GB/s. Keep auto step control, since an underfilled frame down-clocks the GPU. Budget rendering explicitly: 3 ms of a 16.7 ms frame costs about 20% of steps.

**Storage.** Add FP16S as a runtime option behind the `shader-f16` check, and run the full validation suite in both formats. Before relying on it, confirm that every equilibrium the solver writes (init, refill, Zou-He, collision) follows Lehmann's eq. 3 operation order, since the paper says accuracy gains depend on it. Log the adapter's buffer limits and whether f16 conversion truncates on each backend, because the spec leaves both open.

**Physics.** Accept that 3D at 2 million cells means small bodies (16 to 24 cells across), 4D to 6D of clearance and Re below about 700 without LES. That range still covers steady and early unsteady sphere wakes, which suit a demo of wake structure. A D3Q27 toggle is the honest answer to rotational-invariance questions at higher Re.

## Conclusion

The 2D design already made the choices that 3D needs. The population shift that made the 2D kernel accurate is the same one that makes 16-bit storage viable. The single fused dispatch that reached 84% of M5 bandwidth in 2D should hold in 3D, and it leaves the 3D kernel bandwidth bound with no API overhead to recover. The expensive parts of a 3D port sit outside the solver: flag bits and force slots that no longer fit, boundary edges and corners that do not exist in 2D, and a render budget that competes with the solver for bandwidth.

The biggest open question is accuracy. Nobody has measured drag or lift under FP16 storage, WGSL's unspecified rounding, TRT and Bouzidi walls together. This tunnel is well placed to measure it, because it already has fixed-range force validation. A D3Q19 WebGPU benchmark, plus FP16 against FP32 C_D on a sphere, would fill two gaps in the published record: no browser 3D LBM reports MLUPS, and no study reports FP16 force coefficients.
